# PLAN — Infrastructure IT: two sites + IPsec site-to-site (IaC)

Specification: [INFRASTRUCTURE_IT_PROJECT.md](INFRASTRUCTURE_IT_PROJECT.md).
Goal: build Site A and Site B as **code** — one shared code base, one small
site-specific configuration per site — so each student can rebuild their site
on their own computer with `make`, and both sites can be joined by an
IKEv2/ESP tunnel-mode IPsec VPN between two OPNsense firewalls.

## 2. Architecture

### 2.1 Tool choices (engineering decisions — spec §10 leaves them open)

| Concern | Choice | Why |
|---|---|---|
| Hypervisor | **KVM + libvirt** (`qemu:///system`) | OPNsense is FreeBSD → needs a real VM; KVM present; libvirt gives declarative networks/domains |
| IaC engine | **Ansible** 14.5.0 / ansible-core 2.21.5 pinned in `.venv` (collections bundled — no Galaxy dependency, Galaxy was returning HTTP 500 on 2026-10-24) | One tool for provisioning (libvirt), guest config, OPNsense config and tests; same versions on both computers |
| Guest OS | **Ubuntu 24.04 LTS cloud image** + cloud-init (NoCloud seed ISO) | Has `mysql-server` 8.0 (spec says MySQL, Debian ships MariaDB); fast unattended boot |
| Firewall | **OPNsense** (nano image, serial console) | Mandated by spec; config managed as XML (also the required deliverable) |
| Web | **Nginx + PHP-FPM** page that reads MySQL | Spec: Nginx or Apache2; page must display DB data |
| Secrets | `.secrets/` (gitignored), generated by Ansible `password` lookup | No secrets in git; the IPsec PSK file is copied once between students |

### 2.2 Addressing plan (final, shared by both sites)

| Component | Site A | Site B | libvirt name (A / B) |
|---|---|---|---|
| LAN subnet | 10.0.2.0/24 | 10.15.15.0/24 | net `infra-a-lan` / `infra-b-lan` |
| OPNsense LAN (gateway, DNS) | 10.0.2.1 | 10.15.15.1 | `a-opnsense` / `b-opnsense` |
| OPNsense WAN | 192.168.100.11/24 | 192.168.100.12/24 | net `infra-wan` |
| WAN upstream gateway (host bridge) | 192.168.100.1 | 192.168.100.2 (distributed) / .1 (lab) | — |
| VIP (Keepalived) | 10.0.2.100 | 10.15.15.100 | — |
| HAProxy 1 (MASTER) | 10.0.2.5 | 10.15.15.10 | `a-haproxy1` / `b-haproxy1` |
| HAProxy 2 (BACKUP) | 10.0.2.6 | 10.15.15.11 | `a-haproxy2` / `b-haproxy2` |
| Web (Nginx) | 10.0.2.7 | 10.15.15.7 | `a-web` / `b-web` |
| MySQL | 10.0.2.8 | 10.15.15.8 | `a-db` / `b-db` |
| Hypervisor mgmt address on LAN | 10.0.2.254 | 10.15.15.254 | — |
| VRRP `virtual_router_id` | 51 | 52 | — |

All LAN interfaces are /24; every VM's default gateway is its OPNsense LAN `.1`;
the VIP is never statically assigned. VM MAC addresses are derived from the IP
(`52:54:00:<o2>:<o3>:<o4>`) so they are stable and unique across both sites.

### 2.3 Topology on one computer

```text
                  Internet (host Wi-Fi, NAT by libvirt)
                              |
        host 192.168.100.1 ---+--- infra-wan 192.168.100.0/24 (bridge virbr-iwan)
                              |            (distributed mode: + enp3s0 / VXLAN uplink to the other host)
                    WAN 192.168.100.11
                      [ a-opnsense ]
                    LAN 10.0.2.1
                              |
   infra-a-lan 10.0.2.0/24 ---+---------+-----------+-----------+------------ host 10.0.2.254 (mgmt/SSH)
                              |         |           |           |
                       a-haproxy1  a-haproxy2     a-web        a-db
                         .5 (M)      .6 (B)        .7           .8
                              \___ VIP .100 ___/
```

### 2.4 Management path

The hypervisor holds `.254` on each LAN bridge (libvirt *isolated* network: no
forwarding through the host). Ansible reaches the VMs over SSH on that address.
VM traffic to anywhere else (Internet, other site) still goes through OPNsense,
which is verified in Phases 2 and 6 (`traceroute` first hop = `.1`).

### 2.5 Two computers — how the WAN peers meet (decision for Phase 6)

Both OPNsense WANs sit on the same logical segment 192.168.100.0/24 so IPsec
runs without NAT (ESP proto 50 + UDP 500; NAT-T 4500 also opened).

| Mode | How | When |
|---|---|---|
| **lab** (`MODE=lab`) | Both sites on one host share `infra-wan` | Development, CI-style rehearsal, fallback demo |
| **distributed / cable** (default for the defense) | Ethernet cable (or switch) between the two computers; `enp3s0` enslaved to `virbr-iwan` on both hosts | Most reliable; no dependence on campus Wi-Fi |
| distributed / overlay | VXLAN (or GRETAP) over WireGuard across any IP network (phone hotspot) attached to `virbr-iwan` | If no cable is available |

### 2.6 Repository layout

```text
Makefile                     entry points: make setup | phase1 SITE=a ... | test-phase1 SITE=a
ansible.cfg  requirements.txt (ansible + bundled collections, pinned)
scripts/bootstrap-host.sh    one-time sudo: libvirt/KVM packages, groups, docker coexistence hook
inventories/common/          shared: addressing of both sites, IPsec params, VM sizing, image pins
inventories/site_a/          Site A: hosts + site variables
inventories/site_b/          Site B: hosts + site variables
playbooks/                   one playbook per phase
roles/                       hypervisor, libvirt_network, libvirt_vm, opnsense, mysql, webapp, haproxy, keepalived
tests/                       one validation playbook per phase + acceptance.yml
deliverables/                generated: diagram, addressing plan, OPNsense XML, keepalived.conf, haproxy.cfg
.secrets/ .cache/ .venv/     gitignored: keys/passwords, downloaded images, toolchain
```

Usage: `make <target> SITE=a|b [MODE=lab|distributed]`.

## 3. Phases

Each phase ends with an automated test playbook (`make test-phaseN SITE=x`).
A phase is **done** only when its test passes on Site A (and Site B in lab mode).

### Phase 1 — Virtual networks and VMs

Tasks
- [ ] `scripts/bootstrap-host.sh` (sudo, once per computer): libvirt, virtinst, python3-libvirt/lxml, groups, libvirt network hook for Docker coexistence
- [ ] `make setup`: venv with pinned ansible-core, pinned collections, SSH key in `.secrets/`
- [ ] Role `hypervisor`: storage pool `infra`, download + SHA256-verify Ubuntu 24.04 image, upload as base volume
- [ ] Role `libvirt_network`: `infra-wan` (NAT, host `.1`/`.2`) and `infra-<site>-lan` (isolated, host `.254`), no DHCP
- [ ] Role `libvirt_vm`: qcow2 overlay, cloud-init seed (static IP /24, gateway `.1`, DNS `.1`, user `infra`, SSH key), domain XML, start
- [ ] Deploy the four application VMs of the site

Validation (`tests/phase1.yml`)
- networks `infra-wan`, `infra-<site>-lan` active + autostart; 4 domains running
- each VM: `lan0` has exactly its planned address /24; default route via OPNsense `.1`; VIP absent
- **full ping mesh between the four LAN VMs succeeds** (spec test)

### Phase 2 — OPNsense

Tasks
- [ ] Download + verify OPNsense nano image (pinned version), per-site overlay disk
- [ ] Domain with `vtnet0` = LAN (`infra-<site>-lan`), `vtnet1` = WAN (`infra-wan`)
- [ ] Unattended bootstrap over the serial console (pexpect): LAN IP, enable SSH with key
- [ ] Ansible applies the site config (`config.xml` edits): interfaces, WAN static IP + gateway, Unbound DNS, outbound NAT for the LAN, LAN-side GUI/SSH only, then reload
- [ ] Spike first: confirm the config-injection mechanism on the pinned OPNsense version and record it here

Validation (`tests/phase2.yml`)
- OPNsense reachable on `.1` (SSH/HTTPS) from the LAN, GUI **not** reachable from WAN
- each VM: `ping 1.1.1.1`, DNS resolution via `.1`, `apt-get update` succeeds
- `traceroute` first hop from a VM is `.1`

### Phase 3 — Web and MySQL

Tasks
- [ ] Role `mysql`: `mysql-server`, `bind-address` = LAN IP, database `infra`, table with seed rows identifying the site, user `app`@`<web IP>` only
- [ ] Role `webapp`: Nginx + PHP-FPM page querying MySQL (shows site name, rows, DB host, served-by hostname), `/health` endpoint for HAProxy

Validation (`tests/phase3.yml`)
- from web VM: `mysql -h <db> -u app -p` logs in (spec acceptance test 3)
- `curl http://<web>/` contains rows read from MySQL
- `app` user cannot log in from another host (e.g. haproxy1)

### Phase 4 — Keepalived and HAProxy

Tasks
- [ ] Role `haproxy`: frontend `:80`, backend web with `option httpchk GET /health`, stats on LAN
- [ ] Role `keepalived`: VRRP instance, MASTER prio 150 / BACKUP 100, `virtual_router_id` per site, `auth_pass` from secrets, unicast peers, `track_script` on haproxy
- [ ] `net.ipv4.ip_nonlocal_bind=1` so HAProxy binds the VIP on both nodes

Validation (`tests/phase4.yml`)
- VIP on haproxy1 only; `curl http://VIP/` returns the DB-backed page
- `systemctl stop keepalived` on MASTER → VIP on haproxy2 within ~3 s; continuous curl loop shows no outage beyond a few requests; restart → VIP back (preempt)
- stopping `haproxy` on MASTER also moves the VIP (track_script)

### Phase 5 — NAT and firewall

Tasks
- [ ] OPNsense port forwards WAN TCP 80/443 → VIP (with associated, logged pass rules)
- [ ] WAN default deny (logged); explicit no access to 3306/22/GUI from WAN
- [ ] LAN rules minimal: LAN → any (Internet), LAN → OPNsense mgmt
- [ ] Optional: HTTPS on 443 (self-signed cert terminated on HAProxy) so the 443 forward is meaningful

Validation (`tests/phase5.yml`, run from the hypervisor = WAN side)
- `curl http://192.168.100.1x/` returns the page (acceptance test 1)
- `nc -zv 192.168.100.1x 3306` refused/timeout; also 22 and GUI ports blocked (acceptance test 4)
- HA failover still works through the WAN path

### Phase 6 — IPsec tunnel (both students)

Tasks
- [ ] Decide and implement the WAN interconnection between the two computers (§2.5), `make wan-link`
- [ ] Shared IPsec parameters in `inventories/common` (IKEv2, AES-256/SHA-256/DH14, 28800 s; ESP AES-256-GCM, PFS DH14, 3600 s; DPD) + shared PSK file
- [ ] OPNsense IPsec connection (swanctl): local/remote = own/peer WAN, mirrored child SA LAN↔LAN, **no NAT** between LANs (outbound NAT exception)
- [ ] WAN rules: UDP 500, UDP 4500, ESP from peer WAN only; IPsec interface rules: peer LAN ↔ local LAN (ICMP + needed ports)
- [ ] Export `config.xml` of each OPNsense to `deliverables/`

Validation (`tests/phase6.yml` + `tests/acceptance.yml`)
- `swanctl --list-sas` on both: IKE SA ESTABLISHED + CHILD SA INSTALLED with the agreed proposals
- from `10.0.2.7`: `ping 10.15.15.7` succeeds; on B-web `tcpdump` shows source 10.0.2.7 (no NAT)
- all six acceptance tests (spec §7) pass; screenshots collected for the report

## 6. Risks and open points

- **OPNsense automation** is the hardest part (no cloud-init). Mitigation: Phase 2 spike; fallback = documented manual console step + Ansible for everything after SSH is up.
- **Cross-host WAN** on campus Wi-Fi (client isolation likely) → prefer Ethernet cable; lab mode keeps everything testable on one machine.
- **Docker FORWARD DROP** can silently break libvirt NAT → handled by the bootstrap hook; checked in Phase 2 tests.
- Failover covers HAProxy/Keepalived only — not web, MySQL or OPNsense (spec §10). Not claimed otherwise.
